# Performance Audit — AFRERA Platform

## Summary

Scope: `frontend/src/**` (150 feature modules under `frontend/src/modules/M001`–`M150`, `App.jsx`, `store/`, component tree), `backend/src/**` (services, `index.js`, `monitoring/performance.js`), and both `package.json` manifests, audited for bundle-size bloat, inefficient rendering, blocking synchronous I/O on hot paths, and memory-leak-prone patterns (uncleared intervals/listeners, growing caches). Audit is static (grep/read-based); no production `vite build` was run and `backend/node_modules` is not fully installed in this environment (only 1 of 39 declared packages present), so dependency-weight figures below are reference/graph-based, not measured disk sizes — flagged explicitly where that matters.

The platform ships as a single-page React app with **150 route-level feature modules statically imported into one 1,342-line `App.jsx`** and **zero use of `React.lazy`/code-splitting anywhere in the codebase** — every module's JS ships in the initial load regardless of which route the user visits. This is the single largest finding and the main reason for the `warn` status. On the backend, three services perform **synchronous `fs.readFileSync`/`writeFileSync`** as their primary datastore on code paths mounted directly as Express request handlers (`/api/v1/forms`, `/api/v1/analytics`) and inside login/registration — genuine event-loop-blocking I/O under concurrent load. A confirmed **unbounded `Map` growth** memory leak exists in `realtimeMonitoringService.js`, where stopped monitors are marked `stopped` but never removed from `this.activeMonitors`.

On the positive side: the two `setInterval` call sites in `frontend/src` are both correctly cleaned up via `useEffect` cleanup functions, no leaking `addEventListener` calls were found in the frontend, `compression()` middleware is registered on the Express app, and `vite.config.js` already defines `manualChunks` for `vendor`/`ui`/`forms`/`charts` — so library-level splitting exists even though route-level splitting does not.

Overall status: **warn**. Nothing found here breaks the build or crashes the app outright, but the combination of no route-level code splitting at 150-module scale, blocking sync I/O on auth/forms hot paths, and an unbounded-growth cache are real production risks that should be resolved before "launch level" load.

## Findings

### 1. [High] No code-splitting for any of 150 route-level modules — entire app ships in one bundle
- **Location**: `frontend/src/App.jsx` (1,342 lines; 150 static `import ...Page from './modules/M0xx/M0xxPage'` statements, e.g. lines 166–181+); confirmed zero matches for `React.lazy`/`lazy(` anywhere under `frontend/src` (`grep -rl "React.lazy\|lazy("` returns no files).
- **Description**: Every one of the 150 feature-module page components (Insurance, Logistics, Marketplace, IoT, AR/VR, Blockchain Traceability, etc.) is imported eagerly at the top of `App.jsx` and rendered through a single `<Routes>` tree. Vite/Rollup will therefore emit one (or a few, per `manualChunks`) very large JS chunk containing all 150 modules' code, third-party chart/table/form logic they pull in, etc. — a user visiting only the login page and one dashboard still downloads and parses code for all 150 modules. This directly inflates first-load bundle size and time-to-interactive, and gets worse linearly as more modules are added.
- **Remediation**: Convert the 150 page imports in `App.jsx` to `React.lazy(() => import('./modules/M0xx/M0xxPage'))`, wrap the `<Routes>` block in a single `<Suspense fallback={...}>`, and keep the existing `manualChunks` config (`vendor`/`ui`/`forms`/`charts`) for the shared libraries those lazy chunks will still pull in. This is a mechanical, low-risk change given the uniform `export default M0xxPage` pattern already in use.

### 2. [High] Blocking synchronous file I/O on request-handling hot paths (login, register, forms, analytics)
- **Location**: `backend/src/services/authService.js` (`readAuthStore`/`writeAuthStore`, lines 59–85, called from `loginUser` line 408, `registerUser` lines 250/291, and two other call sites at lines 545 and 1160); `backend/src/services/formService.js` (`readStore`/`writeStore`, lines 28–49, plus a `readFileSync` of a schema file at line 64 inside `async function ensureDatabaseSchema`); `backend/src/services/analyticsService.js` (`readFormStore`, lines 21–28). `formService` and `analyticsService` are mounted directly as Express route handlers at `backend/src/index.js:452` (`mountRoute('/api/v1/forms', formService)`) and `:453` (`mountRoute('/api/v1/analytics', analyticsService)`).
- **Description**: These services use `fs.readFileSync`/`fs.writeFileSync` on a JSON file (`auth_store.json`, forms store) as a fallback/primary datastore, invoked synchronously **inside the request-handling path** — `loginUser` and `registerUser` call `readAuthStore()`/`writeAuthStore()` on essentially every login/registration attempt, and the entire `/api/v1/forms` and `/api/v1/analytics` route surfaces read/write the JSON file on each call. Node.js is single-threaded for JS execution; a synchronous disk read + `JSON.parse`/`JSON.stringify(..., null, 2)` (pretty-printed, more CPU than compact) on every such request blocks the event loop for the duration of the syscall and parse/stringify, serializing all other concurrent requests being handled by the same process during that window. Under concurrent login/registration load or a large forms store, this directly caps throughput and creates latency spikes for unrelated requests.
- **Remediation**: Replace with `fs.promises.readFile`/`writeFile` (non-blocking) at minimum. Better: since this data path is explicitly a *fallback* (Postgres is the primary store elsewhere in the codebase), move it fully onto the existing database, or keep an in-memory cache that's populated once at startup and flushed asynchronously/periodically rather than round-tripping to disk synchronously on every request. If the JSON file must remain the source of truth, add a write queue/lock to avoid concurrent-write corruption once reads are made async.

### 3. [High] Confirmed unbounded `Map` growth (memory leak) in `realtimeMonitoringService`
- **Location**: `backend/src/services/realtimeMonitoringService.js` — `startMonitoring()` (lines 100–125, generates a fresh `monitorId` per call via `generateMonitorId` at line 527: `` `monitor_${resourceId}_${Date.now()}` `` and inserts into `this.activeMonitors` at line 114) vs. `stopMonitoring()` (lines 130–148).
- **Description**: `stopMonitoring(monitorId)` sets `monitor.status = 'stopped'` and re-`.set()`s it back into `this.activeMonitors` (line 140) but **never calls `this.activeMonitors.delete(monitorId)`**, and no other code path prunes stopped entries from the map. The per-monitor interval loop (`startMonitoringLoop`, lines 153–187) does correctly self-clear via `clearInterval(loop)` once it observes `monitor.status !== 'active'`, so the *timer* isn't the leak — but the `monitor` object itself (carrying up to 1,000 buffered metric snapshots per `cleanupOldMetrics`, plus an unbounded `alerts` array that is never trimmed) stays resident in the `Map` forever. Because `generateMonitorId` embeds `Date.now()`, every `startMonitoring()` call for the *same* `resourceId` also produces a brand-new map key rather than reusing/overwriting an existing one, so repeated start/stop cycles (e.g., a UI toggling monitoring on/off, or a resource being re-monitored after redeploy) accumulate distinct entries indefinitely. `getAllMonitors()` and `healthCheck()` (which reports `active_monitors: this.activeMonitors.size`) will show ever-growing counts including long-stopped monitors.
- **Remediation**: In `stopMonitoring`, call `this.activeMonitors.delete(monitorId)` (either immediately or after a short grace period if stopped-monitor history needs to be queryable briefly), and add a periodic sweep (similar to the existing `cleanupOldMetrics`/`cleanupOldEvents` patterns already used elsewhere in this same file) that evicts monitors whose `status === 'stopped'` and `stopped_at` is older than some TTL. Also cap/trim `monitor.alerts` the same way `monitor.metrics` is already capped at 1,000.

### 4. [Medium] N+1 sequential-`await` loops on write-heavy hot paths (checkout, sensor ingestion, recommendations)
- **Location**: `backend/src/services/orderService.js:267–277` (loop of `await client.query(INSERT INTO order_items...)` per cart item, inside the order-creation transaction, lines 240–283); `backend/src/services/iotSensorService.js:164–166` (loop of `await getPostgreSQL().query(...)` per sensor reading); `backend/src/services/valueCommerceService.js:408–409` (loop of `await pool.query(...)` per recommendation record).
- **Description**: Each of these issues one round-trip `INSERT` per loop iteration instead of a single batched multi-row insert. In `orderService.js` this sits directly in the checkout critical path, inside a single transaction on one pooled client — a cart with N line items makes N sequential network round-trips to Postgres (in addition to the order-row insert and the cart-delete) before the transaction can commit, directly adding to checkout latency and holding the DB connection/transaction open longer than necessary. The IoT and commerce cases are similar but on ingestion/recommendation-write paths rather than a user-facing request.
- **Remediation**: Replace the loops with a single parameterized multi-row `INSERT ... VALUES ($1,$2,...),($n,$n+1,...)` (built from the array) or a `pg` bulk-insert helper, cutting N round-trips down to 1 per batch. This is a query-shape change only — no schema change needed — but is an implementation change, so verify with `db-auditor`'s existing N+1 findings (`.claude/audits/AUDIT_DB.md`) before fixing to avoid duplicate/conflicting work.

### 5. [Low] Heavy backend dependencies declared but unreferenced anywhere in `backend/src`
- **Location**: `backend/package.json` — `aws-sdk` (v2, monolithic SDK), `elasticsearch` (deprecated client, superseded by `@elastic/elasticsearch`), `apollo-server-express` + `graphql`; also `"crypto": "^1.0.1"` listed as an npm dependency.
- **Description**: `grep -rl "require(['\"]aws-sdk['\"]" backend/src`, the same for `elasticsearch`, and for `apollo-server-express` all returned zero matches — none of these packages are `require()`'d anywhere in `backend/src`. `aws-sdk` v2 is a large monolithic package (bundles clients for every AWS service in one install) commonly flagged for inflating `npm install` time, Docker image layers, and cold-start `require()` resolution when only specific v3 modular clients are actually needed — here it appears entirely unused. `"crypto": "^1.0.1"` is a legacy, long-deprecated npm shim package that shadows Node.js's own built-in `crypto` module; it should never be an explicit dependency (Node's built-in `require('crypto')` is already used correctly elsewhere, e.g. `authService.js:8`). Note: `backend/node_modules` is not fully installed in this environment (1 of 39 declared packages present), so this finding is based on the dependency manifest and `require()` graph, not a measured on-disk/Docker-image size.
- **Remediation**: Run `npx depcheck` against `backend/` to confirm, then remove `aws-sdk`, `elasticsearch`, `apollo-server-express`, `graphql`, and `"crypto"` from `backend/package.json` if truly unused (or replace `aws-sdk` with the specific `@aws-sdk/client-*` v3 modular package if S3/etc. access is planned but not yet wired up).

### 6. [Low] Unused frontend dependency: `socket.io-client`
- **Location**: `frontend/package.json` (`"socket.io-client": "^4.6.1"`).
- **Description**: `grep -rl "socket.io-client" frontend/src` returns zero matches — the package is declared but never imported anywhere in the frontend source. Because it's never `import`ed, Rollup/Vite won't include it in the production bundle (so this is not directly inflating shipped JS), but it is dead weight in `node_modules`/install time and signals a real-time feature that was either removed or never wired up, worth reconciling with the backend's `socket.io` usage.
- **Remediation**: Either remove the dependency, or wire it up if real-time client features (e.g., live shipment/IoT updates currently done via 5s/30s `setInterval` polling in `RealTimeTracking.jsx` and `DeviceMonitor.jsx`) were intended to use WebSockets instead of polling.

### 7. [Low] Negligible use of rendering-optimization primitives at 150-module scale; no list virtualization
- **Location**: Repo-wide `frontend/src` — `grep -rl "React.memo\|memo("` returns 0 files; `useMemo(`/`useCallback(` combined appear at only 7 call sites total across the entire `frontend/src` tree; `react-window`/`react-virtualized` are absent from `frontend/package.json` and unreferenced in source.
- **Description**: Across ~150 feature-module pages and their component trees, essentially no component uses `React.memo`, and derived/computed values or callbacks passed to children are almost never memoized. This isn't a bug in isolation, but combined with Finding #1 (all 150 modules mounted under one router/layout) it means any re-render triggered high in the tree (context updates, layout state, the `zustand` `authStore`) has no memoization boundary stopping it from cascading into expensive child re-renders — notably chart-heavy pages such as `frontend/src/pages/AnalyticsPage.jsx` (the codebase's one `recharts` consumer). No large-list virtualization library is present either, so any module rendering a long table/list (marketplace catalogs, logistics shipment lists, IoT device lists) renders every row's DOM eagerly.
- **Remediation**: Not urgent to apply everywhere, but before launch: add `React.memo` to leaf row/card components in list-heavy modules, audit `AnalyticsPage.jsx` and other chart pages for `useMemo` on chart-input data, and adopt `react-window`/`react-virtualized` for any list/table that can exceed ~100 rows in production data (Marketplace, Logistics, IoT device lists are the most likely candidates — not individually verified row-count here).
