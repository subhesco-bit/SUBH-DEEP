# Route Reconciliation (#48 / #49)

Generated by static extraction + cross-reference against the real, running code — not a manual review of every line. See "Known limitations" before trusting an individual entry.

## Method

- **Backend inventory**: parsed `backend/src/index.js` for every `app.use(path, router)` / `mountRoute(path, service)` call and every `service.setupRoutes(app)` call (29 services), then extracted every `router.METHOD('/path', ...)` inside each resolved file.
- **Frontend inventory**: parsed every `api.METHOD(`...`)` call in `frontend/src/services/api.js`, prefixed with the real axios `baseURL` (`/api/v1`), with `${...}` template interpolations normalized to `:param` the same way as backend `:id`-style params.
- Cross-referenced by normalized `METHOD path`.

## Known limitations (read before acting on the raw lists)

1. **The ~150 `modules/M0XX/*` generated-module routes are not in this inventory at all.** They're loaded via a dynamic directory-walk loop in `index.js`, not a static `app.use(path, var)` call my extractor matches. The earlier concept-document gap analysis already characterized these as "scaffolded CRUD, no dedicated UI" — that finding stands, but this reconciliation doesn't independently re-verify it.
2. Path-param normalization is heuristic (`:id` and `${x}` both become `:param`); a route and a call with the same shape but semantically different param counts could still false-match or false-miss.
3. Every top offender file was spot-checked, not every one of the 1,043/599 entries individually.

## Confirmed real finding (spot-checked, not assumed)

`GET /api/v1/analytics/overview`, `/insights`, `/platform-stats` — called by `frontendAPI.analyticsAPI` and consumed somewhere in the dashboard — resolve to `analyticsService.js`, whose `setupRoutes`-equivalent mount is **already correctly skipped** at boot (`"Skipping route mount for /api/v1/analytics because no router was exported"` — visible in every boot log this session). The reason: `AnalyticsService` never defines an Express router at all. Its `generateReport()` call chain bottoms out in `fetchCropData()`, `fetchFarmerData()`, `fetchRevenueData()`, `fetchExpenseData()`, and ~15 sibling methods that are **100% hardcoded fake numbers** (`return { total: 150, active: 120, ... }`, literally commented `// Mock implementation - would query database in production`).

**This was deliberately left unfixed.** Wiring a real route to this service would mean serving fabricated dashboard data to users — the platform's own no-fabrication discipline (established and enforced throughout this session: see the `Math.random()`-confidence sweep, the escrow-service honesty fixes) says the current behavior — failing to mount rather than lying — is correct.

**Scope correction (2026-08-16):** this was originally estimated as "~20 fetch methods" — that undercounts it substantially. Read in full: **every one of the ~30 `analyze*`/`assess*`/`identify*`/`generate*` helper methods also ignores its real input entirely** and returns a hardcoded literal — e.g. `analyzeCropPerformance(cropData)` never reads `cropData`; it returns `{ top_performing: ['wheat', 'rice'], ... }` unconditionally. This spans 8 unrelated report domains (agricultural, financial, operational efficiency, market intelligence, resource utilization, risk assessment, sustainability, user analytics, supply chain), several of which (operational efficiency, market intelligence, sustainability, supply chain) have no obvious real data source in the current schema at all yet — that's a data-modeling decision, not just a query-writing one. This is a multi-day, multi-domain rewrite, not a bounded afternoon task. Two report types were confirmed to have real, queryable data sources this session (`crops`, `farmers` tables for agricultural overview; `users`, `orders` for user analytics via the same pattern as `platformTelemetryService.js`) — the other six still need a real data-source decision before any code is written for them. Do not rewrite this piecemeal under time pressure; a rushed version would just be fabrication in a different shape.

## Orphan services (not "route with no caller" — "service with no route at all")

Everything above catches a route that exists but nothing calls it. It does **not** catch a
service file that has no route/controller at all — that class of bug was found twice this
session by hand (`productMediaAIService.js`: real, DB-backed AI image/video-script logic, zero
route, zero controller, unreachable from any HTTP request until fixed 2026-08-16;
`completeAIIntegrationService.js`: was mounted, but had ~20 `ReferenceError`-level crash bugs
that would have surfaced the moment any of its 15 endpoints were actually called). Per explicit
user feedback ("if you index all files with no connection you will not have to repeat or
duplicate again and again"), this check is now a rerunnable script instead of manual grepping:

```bash
node scripts/find-orphan-services.js
```

**Result as of 2026-08-16** (172 service files scanned against the full `backend/src` tree):
only `advancedServiceGenerator.js` is unreferenced, and that is correct — it is a dev-time
code-generation template (returns service/route code as strings for scaffolding new modules),
not a runtime capability, so it has no route by design. See the script's own header comment for
what it does and does not prove (reference vs. full reachability from `index.js`).

Re-run this after adding any new service file, and before assuming "the backend has N real
capabilities" in any future audit — it is cheap and catches exactly the kind of gap that looks
identical to a genuinely missing feature until you check.
